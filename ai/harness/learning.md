# 自我学习与优化 (Self-Learning & Optimization)

> 本篇补 `ai/harness/` 的一处空缺：[可观测性](observability.md) 讲怎么**看见**行为，[版本化与灰度](rollout.md) 讲怎么**发布**变更，但没有一篇回答"看见之后怎么让下一版更好"。这里把"跟踪 → 信号 → 提案 → 门禁 → 灰度"这条回路拆开，重点不在"怎么学"，在**怎么让这条回路可证伪**——自学习系统最常见的失败不是学不会，而是学会了错的、还静默扩散。
>
> 范围限定：本篇只谈**治理回路**（跟踪、证据、门禁、退役），不谈学习算法本身。从轨迹里抽可复用条目的算法已有不少工作（见文末「参考」一节），本篇的真差异在把它们做成可灰度、可退役、可审计的一等对象。
>
> 学习产物的写入侧（extract / store / update / forget）见 [AI 记忆系统](../memory.md)；本篇只关心其中 **procedural 层**怎么被 harness 生产、审批、退役。

## TL;DR

- **harness 里的"自我学习"不是让模型变聪明**——权重不在你手里。它是**让下一个版本比上一个好**，产物必须落成**版本化产物**的 diff：manifest 四类对象（模型 / prompt / 工具 schema / harness 配置）、prompt bundle、或经验库的一个 generation。不是版本化产物的东西不可灰度、不可回滚，那只是日志。
- **跟踪的锚点是 decision checkpoint，不是每一步**：[状态管理与 Checkpoint](state.md) §2.1 明说"每步只写 trace 不写 snapshot"，所以判据只能是"失败前最近的 checkpoint + `[锚点, 失败]` 区间 trace + `context_snapshot_hash`"。
- **重放不是复现。** 锁 manifest + `temperature=0` 也做不到逐字段比对（[版本化与灰度](rollout.md) §1），diff 必须是 **N 次重放的分布指纹**，而且要先跑一次"同一 manifest 重放自身"建 flaky 基线。
- **信号有严格优先级**：可验证信号 > 人类干预（先分清 cancel / steer / inject）> 轨迹差分 > LLM-as-judge。未校准的 judge 只能当过滤器，不能当 reward——否则你优化的是一台会漂移的仪表。
- **顺序不能反**：可观测 → 可回放 → 可灰度 → 才谈学习。**头号陷阱是污染**：badcase 被学进 few-shot，评测立刻涨、线上一点没动。

## 1. 先把"学习"这个词拆开

### 1.1 可改的只有三类对象

模型权重在 provider 手里，推理能力不会因为"反思了三轮"而提升。harness 能改的只有这三类，单位收益和风险差一个量级：

| 可改对象   | 具体形态                                               | 变更成本            | 单位收益       | 主要风险                |
| :--------- | :----------------------------------------------------- | :------------------ | :------------- | :---------------------- |
| **接口面** | 工具 `description`、schema 字段名、错误文案、stop rule | 极低（一行字）      | 经验上最高     | 描述写错 → 工具不被选择 |
| **策略面** | prompt 分段、few-shot 集合、压缩策略、重试分类、阈值   | 中（要跑评测）      | 中             | 一次改多段 → 无法归因   |
| **经验面** | procedural 条目（技能 / playbook）、semantic 事实      | 高（要生成 + 维护） | 长尾高、平均中 | 膨胀、过期、污染        |

> **一个经验判断（不是测量结论）**：改工具 `description` 的那一行字，通常比让模型"更仔细地思考"更能改变行为。机制是清楚的——描述文本就是行为输入，[版本化与灰度](rollout.md) §2 已经承认"描述改了也算变更"，那它就是 harness 的**参数**。但"有效一个量级"这类说法我没有实验支撑，别当结论引。

### 1.2 一次"自我学习"成立的必要条件

> ① 可归因（能指到具体 step 与 prompt 段）；② 作用域明确（runtime / tenant / task_family / agent）；③ 带失效条件（什么时候该退役）；④ 能进入**版本化产物**并整代回滚；⑤ 假设能指回 trace evidence。

三个容易读错的地方：

- **这是必要条件集，不是定义。** 一个凭直觉改 prompt 的人同样能满足前四条——区别在第 ⑤ 条：有没有证据链，决定它是"学习"还是"发布"。
- **④ 的"版本化产物"比 manifest 宽**。经验库的 generation（[AI 记忆系统](../memory.md) §15.3 的 publish / retire）同样是版本化产物：整代回收 = 回滚。硬要只认 manifest diff，会把本篇 §4.3、§5 全部判成非法。
- **④ 也别窄读成"配置"**。[版本化与灰度](rollout.md) §2 的 `harness@v22` 装得下 harness 代码，检索索引、工具实现同理——真正被排除的只有"没人能回滚的自由文本建议"。

## 2. 跟踪：三类数据，缺一类就断链

| 数据层                                    | 回答什么                       | 关键字段                                                                                     | 出处                                                                                       |
| :---------------------------------------- | :----------------------------- | :------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------- |
| **span 树**                               | 哪一步、哪一行 prompt 出了问题 | `trace_id / parent_span_id / turn / agent / tool_calls[].args_hash / stop_reason / cost_usd` | [可观测性](observability.md) §1（schema 择要）                                             |
| **checkpoint（FSM 快照）+ 副作用 outbox** | 当时的世界状态、哪些动作已发出 | `step_id / fsm_state / state_payload / idempotency_key`                                      | [状态管理与 Checkpoint](state.md) §2–§3                                                    |
| **eval manifest + dataset row**           | 对照组存不存在、能不能重演     | `manifest` / `origin_trace_id` / `expected_trajectory`                                       | [版本化与灰度](rollout.md) §2.1（manifest）+ [可观测性](observability.md) §5（后两个字段） |

### 2.1 锚点是 decision checkpoint，diff 是分布

> [状态管理与 Checkpoint](state.md) §3 的最小不变量（state 快照 + 已发副作用日志 + trace 写到同一时刻）在这里多一层含义：它不只是 resume 的前提，**也是"改完再验同一个场景"的前提**。

但"同一个场景"不等于"同一份逐字段输出"。两条被引笔记都在提前否掉这个假设：

- [版本化与灰度](rollout.md) §1：「`temperature=0` 也不是确定性执行（浮点累加、推理引擎版本、batch 组成都会影响），想"重跑一遍看看"是不可靠的」。
- [状态管理与 Checkpoint](state.md) §5：「完全可重放需要**记录 response** 而不是"再调一次"」。

所以可执行的形状是：**锚点 + N 次采样的分布指纹**，而不是一次 diff。

```text
锚点     = 失败前最近的 decision checkpoint（state §2.1：不是每一步都有 snapshot）
场景     = [锚点, 失败] 区间 trace + context_snapshot_hash + response 缓存（state §5）
基线     = 同一 manifest 重放自身 N 次 → flaky 本底（工具序列 top-1 变化率 / 步数分位）
对照     = 新 manifest 重放同一场景 N 次 → 只在超出 flaky 本底时才立案
```

> N 取 5–10：太少分不出漂移与噪声，太多则每次门禁都在烧钱。**flaky 基线必须先建**——跳过它的行为 diff，会把"这个 case 本来就不稳"记成"新版本把它改坏了"。

### 2.2 两个必须自己动手的动作

- **显式建 span 并设 parent**。框架的"自动 trace"多半是自动 log：它记录"调了一次 LLM"，但没有"这次调用是上一次的孩子"的语义（[可观测性](observability.md) §2.2）。归因链断在这里，学习就没有起点。
- **prompt 分段打 tag + 记 hash**（`<SEG id="retrieved">`、`<SEG id="fewshot_3">`）。失败能定位到"是不是这段 retrieved 内容触发的"之后，"改哪一段"才是个有答案的问题。没有 tag 的 prompt 只能整段重写——而整段重写恰好是**一次改多个变量**的反模式。

### 2.3 一条失配的 trace 就是一条不可执行的经验

> 判据：**这条失败 trace 能不能映射到 manifest 的某个字段？** 能，它是一条经验；不能，它是一条工单（交给改 harness 的人），不是一个学习信号。

把这两类分流很重要：把"harness 缺能力"的失败硬塞进经验库，会让经验库里堆满"下次注意 XX"这种没人能执行的条目，然后所有人的结论变成"自学习没用"。但要小心反例——**夜间批处理 agent 的失败常常是上游水位错位**，它映射不到本 run 的字段，却指向一份需要更新的上游契约：这种应当升级成"跨系统工单"，而不是被就地丢掉。

## 3. 从跟踪到可学习信号

### 3.1 信号优先级

| 信号                                                                         | 获取成本 | 系统偏差 | 适合学什么                                           |
| :--------------------------------------------------------------------------- | :------- | :------- | :--------------------------------------------------- |
| **可验证信号**（测试通过 / exit code / schema 校验 / 工具返回码 / 幂等命中） | 极低     | ≈0       | "这条路走不通"、"这个参数格式不对"——最硬的负样本     |
| **人类干预**（steer / 注入新指令，不含纯取消）                               | 已付过   | 低       | 偏好与边界：用户真正想要什么                         |
| **轨迹差分**（步数 / 工具序列 / token 斜率 / 拦截率）                        | 低       | 中       | 效率与绕路，[版本化与灰度](rollout.md) §5 的"早信号" |
| **用户负反馈 / 客诉**                                                        | 中       | 高       | 价值判断，样本稀疏                                   |
| **LLM-as-judge**                                                             | 低       | 高       | 只当 filter / 排序，不当 reward                      |

### 3.2 三种中断，只有两种是标注

[Harness I/O：流式 / 中断 / HITL / 通道](io.md) §3.1 把用户中断分三种语义，混起来就会把噪声写成 preference pair：

| `intent_kind` | 用户的意思          | 带新指令？ | 进了经验库会怎样                             |
| :------------ | :------------------ | :--------- | :------------------------------------------- |
| `cancel`      | 停掉，别再做了      | 否         | 把"等太久按停"学成"这个任务不该做"——纯毒样本 |
| `steer`       | 换个方向继续做      | 是         | 可用的偏好对                                 |
| `inject`      | 补充信息 / 纠正前提 | 是         | 可用的偏好对                                 |

只有 `steer` / `inject` 携带 `(原计划动作, 新指令, 生效边界)` 这个三元组——io.md 的原话是"把新指令合入当前 turn 的下一**段** prompt 边界"，`cancel` 走的是取消 + 补偿，没有"新指令"这一项。

**工程动作**：三种中断都落结构化事件，字段 `intent_kind` / `before_plan_hash` / `after_instruction`（脱敏，见下）/ `boundary_step_id`；只有前两类进 §5 的 `evidence`，`cancel` 单独计入延迟与 UX 指标。这是整条链路上性价比最高的一张表（经验判断），但前提是分类先做对。

> **合规约束**：`after_instruction` 是用户原话，`evidence.trace_ids` 指向完整 trace。按 [Agent 平台化](platform.md) §5 的口径，正文脱敏、只留 digest 与摘要，审批记录进同一条链。**派生出的经验条目不得跨租户复用其 evidence**——那是用户数据跨租户流动，不是"推广经验"。

### 3.3 为什么 judge 只能当 filter

[评测](../evals.md) 的判据是硬的：**没人算过 judge 与人工的 κ，它的分数只能用来大概排个序**；"κ < 0.6 就只当排序参考，不能当门禁阈值"——注意它**仍然允许排序**，禁的是当门禁。

而 RL 式的自优化会把 judge 的偏置（位置偏置、长度偏置、家族偏好、风格偏好）**放大成策略**——你优化得越充分，偏离真实目标越远。

> 正确用法：judge 当**过滤器**（把 1000 条 trace 缩到 30 条值得人看的），人工或可验证信号当**裁判**。把两者的角色反了，就是用一个漂移的仪表当刹车。

## 4. 学习回路：一条管线，四种作用域

### 4.1 管线形状

```text
trace ──→ 归因四元组 ──→ 最小可重演场景（锁 manifest + response 缓存 + N 次采样）
                              │
                              ▼
                     假设（改哪个字段，指回 evidence）
                              │
                              ▼
     提案 ──→ 门禁（分布指纹 diff + 离线评测）──→ 灰度 ──→ 新 trace 回写
```

对应关系要分清：**manifest 决定"哪一版"，N 次采样决定"这一版稳不稳"，flaky 基线决定"这次差异算不算数"**。三者缺一个，diff 就是在噪声上做判断。

四次跑同一条管线，只换**作用域**与**审批等级**：

| 作用域                    | 生效时刻 | 典型产物                                                   | 审批                   |
| :------------------------ | :------- | :--------------------------------------------------------- | :--------------------- |
| **L1 run 内**             | 秒–分钟  | retry 换 prompt、replan、steer                             | 自动（受终止条件约束） |
| **L2 跨 run（同 scope）** | 小时–天  | per-scope prompt 段、阈值、semantic 事实、badcase → 回归集 | 写入门禁 + 事后抽检    |
| **L3 离线批量**           | 天–周    | 重写 prompt 段 / 工具 `description` / few-shot 选择        | 提案制，人工或门禁批准 |
| **L4 全局（跨租户）**     | 周       | 工具 schema、默认阈值、经验条目的默认集                    | 人工 + 全量 canary     |

> L2 与 L4 的界线是**blast radius**，不是抽象层级。同一句"别用 grep 找定义"，写进 per-tenant prompt 段是 L2，改 `tools@v14` 的全局描述就是 L4——后者一次影响所有租户，必须走全量灰度。

### 4.2 L1：run 内的学习只有一件事值得做

[韧性](resilience.md) §2（尤其 §2.2）的结论是"**换 prompt 不换时间**"：在确定性约束下，同一个 prompt 重复发 5 次通常得到 5 个结构相似的错误答案，改一句提示往往就过了。所以 L1 的学习信号只有"这次为什么错"，动作只有三个：重试（换措辞 / 换工具）、replan、等用户 steer。

**关键点**：L1 的反事实采样已经有现成通道——[状态管理与 Checkpoint](state.md) §5 的时间旅行调试就是"从某个决策点分叉，重跑之后的步骤"。"如果当时选 B 会怎样"不是玄学，是可执行的实验，而且比"让模型反思当时为什么选 A"信息量高一个量级：

> 反思给的是一段**自我陈述**，replay 给的是一次**可比较的轨迹**。先建 replay，再谈反思。

### 4.3 L2：跨 run 的沉淀要先解决"写哪里"

同一条经验可以写在三个地方，代价、污染面和失效方式完全不同：

| 落点                            | 生效范围          | 失效方式                                      | 适合什么                   |
| :------------------------------ | :---------------- | :-------------------------------------------- | :------------------------- |
| **per-scope prompt 段（静态）** | 单租户 / 单 agent | 发新 prompt bundle                            | 领域约束、输出格式、禁止项 |
| **procedural 条目（可检索）**   | 按 scope          | 退役 / 整代回收（memory §15.3 的 generation） | "这类任务先读 A 再看 B"    |
| **工具 `description` / schema** | 全租户（L4）      | 发新 manifest                                 | "什么时候别用这个工具"     |

**优先改静态的、能整代回收的**：它的生效与回收都是版本操作，天然可回滚。可检索的 procedural 条目是最难维护的一种——它要解决"什么时候被召回"和"什么时候该忘"两个问题，而后者通常是没人做的那个。

### 4.4 L3：离线批量优化的纪律

这一层最像"训练"，所以最容易破坏纪律：

- **冻结 eval**：评测集版本 + 不可变 hash 先锁死，再开始优化（[评测](../evals.md) 的评测集设计原则）。
- **proposal 而非写入**：产物是待审的 manifest diff，不是直接上线的新 prompt。
- **一次一个变量**：同时改 prompt 和模型，任何结果都无法归因（[版本化与灰度](rollout.md) §7）。
- **成本也是目标**：优化成功率导致单 run 成本涨 40%，在 [版本化与灰度](rollout.md) §6.2 的阈值下本来就该回滚（注意它的指标是**成本**，不是 token——缓存命中率不同，两者不等价）。
- **先过功效门槛**：样本量撑不起最小可检测效应时，优化结果不可判定（见 §5.2），此时只能攒数据，不能出提案。

> 一个容易被忽略的约束：L3 的每次评估本身要吃预算，而且往往是**双份**（新旧两个 manifest 各跑一遍）。这和 shadow 阶段的双份成本是同一笔账，要在预算树里预留（[Agent 平台化](platform.md) §4）。

## 5. 经验条目的数据模型（procedural memory）

[AI 记忆系统](../memory.md) 把 procedural 层写在表格的一行里——那是分层图的需要，不是工程形态。真要做自学习，它得是一等对象：

```json
{
  "id": "exp_2026_11_03_codesearch",
  "scope": {
    "runtime": "prod",
    "tenant": "t_42",
    "agent": "coder",
    "task_family": "repo_edit"
  },
  "trigger": {
    "kind": "tool_sequence_prefix",
    "match": ["grep", "read_file", "grep"],
    "error_class": "edit_conflict"
  },
  "action": {
    "target": "prompt_segment",
    "pointer": "prompt@sha256:7c1e/segment:tool_hints",
    "base_manifest": "anthropic/claude-sonnet-5-5@2026-09-01 | tools@v14 | harness@v22",
    "diff": "add: '定位定义时优先用 search_symbol，grep 只用于字面量搜索'"
  },
  "evidence": {
    "trace_ids": ["0af76519", "b7ad6b71"],
    "manifest_ids": ["run_9f3", "run_9f8"],
    "case_id": "reg_2026_10_28_007",
    "n": 14,
    "denominator": 2100,
    "counterexamples": 3,
    "mde": 0.08
  },
  "expected_effect": {
    "metric": "steps_per_task",
    "direction": "down",
    "threshold": 0.15
  },
  "validity": {
    "activated_at": "2026-11-03",
    "revalidate_by": "2026-12-03",
    "expires_if": "model_major_bump"
  },
  "status": "proposed",
  "owner": "u_77",
  "provenance": {
    "origin_run": "run_9f3",
    "approved_by": "u_77",
    "ticket": "CHG-1234"
  }
}
```

### 5.1 四条硬约束

1. **`action` 必须是 diff，且带 `base_manifest`**。"下次遇到这个错误先读一下日志"这种条目没有执行器，也没有回滚动作——它只能靠人记住，而"靠人记住"就是没有 harness。`base_manifest` 缺失时，evidence 与 action 分属两套版本，条目不可审计。
2. **必须有退役路径和责任 `owner`**。忘掉比记住难做（[AI 记忆系统](../memory.md) §15.5）；而"有界块很容易变成没人维护的第二个 prompt"（同篇 §15.3，主语是 resident profile block 这类**有界**块——无上限的经验库只会更糟）。`revalidate_by` 到期要**自动进 review queue**，不只是把 `status` 降一级：没有 owner 的降级等于没人处理。
3. **`scope` 决定推广成本，`task_family` 决定可比性**。只有 tenant 没有 task_family，就做不出"同类任务"的分母；而 [版本化与灰度](rollout.md) §3.2 已经警告过"某类任务彻底坏掉但占比只有 2%"——平均数会把它盖住。
4. **派生数据不跨租户**。`after_instruction`、trace 摘要、evidence 都是用户数据侧产物；跨 scope 复用要重新脱敏并重跑一次 L4 灰度，不能靠"推广经验"的名义直接搬。

### 5.2 功效门槛：撑不起阈值就只能当 hint

> 经验条目最容易自欺的一步：拿十几条命中宣布一个百分比改善。`n=14` 配"步数下降 15%"在统计上不可判定，而这类条目一旦被批准，就会在 §6 死法 4 的路径上扩散。

落地口径：

- 每条条目记 `n` / `denominator`（命中数 / 同类 run 数），不是光秃秃的 `support`。
- 按 `task_family` 算最小可检测效应（MDE）——per-scope 样本天然少，**多数条目的真实 MDE 是两位数百分比**，凡是 `threshold` 小于 MDE 的条目，判定为"不可测"。
- 不可测的条目**可以留在库里当检索 hint**（省 token、给模型一点倾向），但**不得进 proposal**、不得写成"已验证有效"。
- 反例数单独记：3 条明确反例比 14 条正面命中更能否决一个条目。

> 这条约束的副作用要提前认：P2 阶段很可能会发现**大部分条目达不到门槛**。届时的正确结论是"经验库降级为 hint 检索"，而不是把 MDE 调低。

### 5.3 腐化的先行指标

> 经验库在腐化时，**成功率通常还不掉，先掉的是"被召回的东西没人引用"**。

主指标用 [上下文工程](../context_engineering.md) 的**信息命中率**（被最终输出引用的 chunk / memory 比例，< 30% 即装配冗余，> 90% 但质量低即装配太窄）。token 斜率（[版本化与灰度](rollout.md) §5）只作交叉验证：它的归因不唯一（压缩失效、工具返回变长都会拉高），而且**条目一次都没被召回时斜率为 0，腐化完全不可见**。

## 6. 五个死法

1. **Goodhart**：优化的是 judge 分数而不是任务成功率。→ 冻结 eval + `last_known_good` 标记（[版本化与灰度](rollout.md) §3.1 / §6.1）+ regression budget（[评测](../evals.md)），judge 只当 filter。它的另一种形态是**离线涨、线上不动**——eval 与线上分布脱节，只有 shadow set 能看出来。
2. **污染**：badcase 被学进 few-shot / memory，评测集分数立刻涨、线上不动。→ 数据血缘隔离：进过 eval 集的 case 打标，prompt / memory 侧物理读不到；这条比任何指标都值得先做。
3. **一次改两个变量**：换模型 + 改 prompt 同时上，任何结果都无法归因（[版本化与灰度](rollout.md) §7）。→ 一个提案只改一个字段，回滚整组。
4. **静默扩散**：在一个租户/任务族上学到的被全局复用。→ 由 `scope` 决定生效范围；跨 scope 推广走独立 L4 canary，并重新脱敏（§5.1 第 4 条）。
5. **把 provider 静默升级当自己的学习成果**：模型 id 没变、权重变了。→ [版本化与灰度](rollout.md) §6.4 的行为指纹就是分辨器：固定金标 case 定期跑生产 manifest。

> 五个死法里只有第 1 个是"优化错了"，其余四个都是"**验证错了**"。这也解释了为什么这一层的第一性投入应该压在评测与回放上，而不是压在"更强的学习算法"上。

## 7. 反直觉

- **模型越强，外挂经验的收益可能越低。** 这是从 [AI 记忆系统](../memory.md) §3 的一条结论类比过来的：原话是"底层 LLM 越强，**memory 系统的**相对收益越低"（因为模型自己越擅长 implicit 抽取与跨轮聚合）。外推到"harness 端自学习"是我的**类比，不是那条结论**。即便如此，方向上的判断仍然成立：强模型下自学习的价值更多集中在少走弯路、少花钱、不越权、能验收上，而不是"答得更好"。
- **自学习系统的第一杀手不是"学不会"，是"学会了错的并且静默扩散"。** 所以阶段顺序不能反：可观测 → 可回放 → 可灰度 → 才谈学习。这和 [可观测性](observability.md) 的"上线前先解决观测"是同一条纪律，只是被"自我进化"的叙事放大了。
- **`finish_reason=stop` 不可信，同理"任务成功"也不可信。** 语义层的验收条件不写清楚（[控制循环](control_loop.md) §4 的分层防御），学习信号本身就是错的——**你会在一个错误的目标上收敛得很好**。
- **反思最贵的不是 token，是不可验证。** 同一份 trace 能被 replay 打脸，但不能被反思打脸。
- **"自动选策略"应当被明确拒绝。** [AI 记忆系统](../memory.md) §14.7 把它列为反模式："meta-learning 听起来美，实际不可控、不透明"。自学习该优化的是**提案质量与审批成本**，不是绕过审批。
- **经验库的规模上限应该写进配置，不是写进文档。** 和 badcase 集一样：没有上限和淘汰机制，跑一次评测就要一天（[评测](../evals.md)）。

## 8. 落地顺序

| 阶段   | 做什么                                                                                            | 为什么是这个顺序                                 |
| :----- | :------------------------------------------------------------------------------------------------ | :----------------------------------------------- |
| **P0** | 四元组归因 + prompt 分段 tag + decision checkpoint 锚点 + 每 run 落 manifest                      | 没有这几样，后面每一步都在猜                     |
| **P1** | 冻结 eval 集 + `last_known_good` + **flaky 基线** + 分布指纹行为 diff + badcase 回流管线          | **没有对照组就不该谈学习**——这是唯一能证伪的装置 |
| **P2** | 只放行 **per-scope 生效**的对象：per-tenant prompt 段、per-scope 阈值；写入门禁 + 事后抽检        | 单位收益高、回滚便宜、blast radius 限在单租户    |
| **P3** | procedural 一等对象（§5 的 schema + 功效门槛 + 退役）+ 全局工具 `description` 重写 + 离线批量优化 | 到这一步才有足够 trace 与样本撑起"可测的条目"    |
| **P4** | 才谈自动生成技能 / 在线探索 / 自建 playbook                                                       | 前三层的闸门没成型时，这层只会加速漂移           |

> 唯一诚实的进度条：**"上周的 badcase，多久变成了 ① 一条有名字的回归用例，或 ② 一条带 evidence 的经验条目？"** 周期长于一周，这条回路就在脱轨。

## 9. 上线前自检

- [ ] 每条失败 trace 的锚点是 decision checkpoint + `[锚点, 失败]` 区间 trace + `context_snapshot_hash`（不要求 step 级 snapshot）
- [ ] prompt 分段有 tag + hash，失败能定位到段而不是整个 prompt
- [ ] 每个 run 落 manifest，能回答"这个 badcase 跑的是哪套版本组合"
- [ ] 行为 diff 是 N 次采样的分布指纹，且先用"同一 manifest 重放自身"建了 flaky 基线
- [ ] replay 走 response 缓存，不是"再调一次"
- [ ] 评测集与 prompt / memory 有物理隔离（进过 eval 的 case 不会进 few-shot）
- [ ] judge 与人工的 κ 算过；κ < 0.6 时只用于排序，没有当门禁
- [ ] 经验条目有 `scope` / `task_family` / `evidence`（含 `n` 与分母）/ `validity` / `owner` / `action.diff`，且能退役
- [ ] 每条的 `threshold` 与 `task_family` 的 MDE 比过；不可测的只当 hint，没进 proposal
- [ ] 中断事件带 `intent_kind`，`cancel` 没有进经验库
- [ ] 派生数据（中断原话、trace 摘要、evidence）有脱敏与 digest，跨 scope 复用前重新脱敏
- [ ] 经验库有规模上限与淘汰策略；信息命中率与 token 斜率都在 dashboard 上
- [ ] 学习类提案走同一条灰度通道（shadow → canary），不是"直接改线上 prompt"

## 参考

从轨迹里抽可复用条目这件事本身不新，重发明一遍会很尴尬。与本篇最相关的几支：

- **ExpeL**（Zhao et al., 2023）：从成败轨迹里抽取自然语言 insight，跨任务复用。本篇 §5 的 `trigger` / `action` 与它的 insight 条目同源。
- **Agent Workflow Memory**（Wang et al., 2024）：把成功的动作序列直接沉淀成可复用 workflow。对应本篇 §4.3 的 procedural 条目，且比"自由文本经验"更接近可执行形态。
- **GEPA / DSPy**：批量式 prompt 优化——用反思式变异 + 评测反馈搜索 prompt，而不是在线学。对应本篇 §4.4（L3），也是"必须有冻结 eval 才能跑"的现成证据。
- **Voyager**（Wang et al., 2023）：技能库 + 自验证。对应本篇 §1.1 的接口面（工具即技能）与 §8 P4。
- **Reflexion**（Shinn et al., 2023）：run 内自我反思。对应本篇 §4.2（L1），也是"反思不可验证"那条反直觉的对照。
- **ACE**（Agentic Context Engineering, 2025）：playbook 的增量演化与去重。对应本篇 §5 的条目演化与 §5.3 的腐化问题。

> **本篇与它们的真差异只有治理面**：条目是版本化产物、有 scope、有 MDE 门槛、有 owner 与退役、走灰度通道。算法层面基本是重组。写这篇的动机也在这里——多数实现把"抽经验"做成了 prompt 技巧，没做成发布流程。
