# Agent 平台化 (Agent Platform)

> 前面几篇讲的都是"一个 agent 怎么跑"——控制循环、沙箱、状态、观测、I/O、生命周期。本篇换到更高一层：**当 agent 变成要卖给多个业务方、要按部门分摊成本、要过合规审计的"平台能力"时，多出来的那层东西是什么。**
>
> 只读一篇就够的话：读 §4 预算树和 §6 边界规则——这两处是"单机能跑"和"平台能运营"的分水岭。

## TL;DR

- 平台化不是"给 agent 加个 API"，是**把租户身份贯穿控制面 / 数据面 / 审计面**；三面任一面的切分不成立，平台就不成立。
- 隔离按成本分四档，**先做行级逻辑隔离 + 强制标签**；物理隔离只给监管与大客户，顺序反了先亏钱。
- 配额与成本护栏必须做成**预算树**（预留 + 结算 + 硬上限）。扁平的 per-session budget 在 fan-out 下会超支 N 倍。
- 执行引擎只有一条不可协商的边界：**模型不直连外部，所有副作用过工具网关**。其余组件（调度器、状态机、检索、护栏）都应可替换。
- 审计是**只追加的事件日志**，且必须能单独回答"谁、哪个租户、哪个 agent、哪次 run、调了什么、谁批的"——少一个字段，事故复盘就退化成猜。

## 1. 什么时候真的需要平台化

单租户也能跑得很好；租户层一旦引入，每条排障路径都变长。触发条件：

- 两个以上业务方共用同一套执行引擎（模型额度、工具凭证、沙箱池）
- 需要按部门 / 客户分摊 token 与工具成本
- 需要对外售卖或对内做"自助接入"（业务方自己配 prompt、自己接工具）
- 有合规诉求：数据出域、操作留痕、事后追责

四个都还没有时，正确做法是**先别做**——把 `tenant_id` 写进接口但只填一个值，等第二个业务方出现再打开，比提前设计一套租户体系便宜得多。

> 反过来说：**已经有两个业务方在共用一个集群时，`tenant_id` 必须第二天就补齐**。跨租户泄漏（缓存 key、向量库 collection、临时目录）不是"以后再说"的技术债，是一次事故就下线的品类。

## 2. 三个面：同一份身份，三种用法

| 面         | 承载什么                                                    | `tenant_id` 的作用         |
| :--------- | :---------------------------------------------------------- | :------------------------- |
| **控制面** | 租户与成员、RBAC / ABAC、配额、配置与发布、凭证托管         | 决定"谁能改什么"           |
| **数据面** | run 调度、队列分桶、存储命名空间、向量库分区、缓存 key 前缀 | 决定"哪些数据能碰哪些数据" |
| **审计面** | 事件日志、trace 标签、审批记录、导出                        | 决定"事后能不能说清"       |

判断标准只有一条：

> **任意一条 trace / 事件日志 / 计费记录单独捞出来，能不能不 join 任何表就说出它属于哪个租户？** 不能，就说明身份在某个环节掉了——通常是异步任务、回调、批处理这三处。

**凭证托管是控制面里最容易做错的一块**：工具（GitHub / 数据库 / 支付）的凭证必须 per-tenant 托管、短期签发、用完即弃；一个共享 service account 会让审计面直接失效——日志里所有操作都是"平台自己"干的。

## 3. 隔离：四档，按成本排序

| 档                  | 做法                                                                      | 增量成本 | 什么时候值得                     |
| :------------------ | :------------------------------------------------------------------------ | :------- | :------------------------------- |
| **1. 行级逻辑隔离** | 所有表带 `tenant_id` + 强制 where / RLS；code review 与静态检查拦住遗漏   | 低       | 默认档，永远要做                 |
| **2. 命名空间隔离** | 队列分桶、对象存储前缀、向量 collection、缓存 key 前缀、临时目录          | 低       | 默认档，和第 1 档一起上          |
| **3. 资源隔离**     | cgroup / k8s namespace、专属 worker pool、per-tenant 令牌桶、专属模型配额 | 中       | 有租户开始"打满"或成本要精确分摊 |
| **4. 物理隔离**     | 独立数据库 / 独立集群 / 独立 VPC / 独立部署                               | 高       | 监管行业、大客户合同要求         |

三个高频泄漏点，都不在业务表里：

- **缓存**：`cache_key = f"user:{uid}"` 少了 `tenant`，A 租户的热数据会喂给 B 租户。
- **向量库**：collection 粒度太粗 + 检索时忘了过滤，`top-k` 里混进别人的 chunk（`rag.md` 里 pgvector 的 `WHERE tenant_id=...` 就是为这个）。
- **临时工作区**：沙箱的 `/tmp`、克隆下来的仓库目录共用了同一个父路径，清理策略一错就互相踩。

> **隔离强度 = 终止难度**（同 [Agent 生命周期与 Harness 承载](lifecycle.md) 里子 agent 的取舍）。租户边界越强，跨租户调度越难做——所以第 2 档是收益最高的那一档：几乎不加调度复杂度，把泄漏面砍到只剩"忘了加前缀"。

## 4. 配额与预算树

配额回答"一次能用多少"，预算回答"总共能花多少"。两者都要做，但**预算是平台化的真门槛**。

### 4.1 配额维度

- 并发 run 数（防 OOM / 防挤爆别人的沙箱池）
- token / 月 与 工具 QPS（防单租户吃光模型配额——对应 [韧性](resilience.md) §5 的三个限流维度）
- 存储与检索量（向量库、对象存储、事件日志保留期）
- 输出带宽 / 导出频率（防把审计数据当导出通道用）

### 4.2 预算树：为什么扁平预算一定超支

成本近似：

```text
Cost ≈ Σ_agent Σ_turn (input_tokens + output_tokens) × price + tool_cost + retrieval_cost
```

注意它是**双重求和**。一个 `budget_usd_per_session` 变量只约束了最外层，子 agent 各自持有一份就意味着 fan-out 出 10 个就是 10 份预算：

```text
[tenant budget] --reserve--> [run budget] --reserve--> [sub-agent budget]
       |                          |                            |
       +--- settle on finish -----+--- unused returns ---------+
```

规则（按重要性排序）：

- **先 reserve 再启动**：进入子 agent 前按"预估上界"占总预算，拿不到就**不启动**（fail-closed），而不是"先跑再记账"。
- **结算归还**：子 agent 结束后按实际值 settle，未用完的部分**立刻**归还父预算；否则一次保守预估会永久锁死额度。
- **子 agent 不能自建预算**：只能从父节点切分，杜绝"自己给自己批钱"。
- **并行 fan-out 的预估按最坏情况 × N**：`Parallel` 拓扑（见 [多 Agent 编排](../multi_agent.md) §3.2）没有共享 state，也没有共享预算——N 个子 agent 同时 reserve，父预算必须够 N 份。
- **计量只有一份实现**：模型网关出 token 数、工具网关出工具成本，编排层只做汇总；两处各算一遍必然对不上账（实现见 [可观测性](observability.md) §3）。
- **80% 告警、100% 暂停而不是 kill**：暂停才能 checkpoint + 转人工（见 [状态管理与 Checkpoint](state.md)），kill 掉就只剩一个无法复盘的失败 run。
- **按分位数设阈值，不按均值**：成本是**幂律分布**的——少数超长 run 吃掉大部分预算。所以预算树的首要作用是**长尾保护**（阻止单 run 跑飞），不是"管住平均开销"；用均值设计阈值，会在月中就撞上限。先量一下自己的 P99/P999 再定数，不同产品差一个量级。

### 4.3 超限的动作阶梯

从最便宜到最贵，命中即停：

1. **排队**：不拒绝，降低并发（适合交互式、有耐心的场景）
2. **降档**：切同家族小模型 / 关掉可选工具 / 减少检索 top-k
3. **压缩**：上下文摘要、截断历史（见 [上下文工程](../context_engineering.md)）
4. **暂停转人工**：高危任务在预算边缘不应自动继续
5. **拒绝新 run**：租户级熔断，返回可解释的结构化错误

> 反面教材：预算到顶直接抛 500。用户看到的是"平台坏了"，实际是"你超标了"——**超限必须是一次可解释的业务事件**，带剩余额度、重置时间、升级入口。

## 5. 审计

### 5.1 事件模型

只追加（append-only），一行一个已发生的事实：

```json
{
  "ts": "2026-10-27T09:12:03.421Z",
  "event_id": "evt_01J...",
  "prev_hash": "sha256:...",
  "tenant_id": "t_42",
  "actor": {
    "type": "agent",
    "agent_id": "coder",
    "run_id": "run_9f3",
    "parent_run": "run_9f0"
  },
  "action": "tool.call",
  "tool": "github.create_pr",
  "args_digest": "sha256:...",
  "args_preview": "repo=acme/api, base=main, files=3 (preview redacted)",
  "policy": { "decision": "allow", "rule": "pr_only_no_direct_push" },
  "approval": { "required": true, "approved_by": "u_77", "ticket": "CHG-1234" },
  "result": "ok",
  "idempotency_key": "run_9f3:create_pr:1"
}
```

### 5.2 四条硬约束

- **不可篡改**：hash chain（`prev_hash`）或 WORM 存储；至少做到"业务库能改，审计库不能改"。
- **与业务数据分离**：审计查询不许扫业务主库——出事时业务库可能已经是一团糟。
- **参数留摘要 + digest**：正文脱敏（PII / 密钥），但保留 hash 以便事后与已知样本比对。
- **审批记录进同一条链**：谁批的、批的工单号、批的时候展示的是哪个版本的参数——分开存就会出现"批的是 A，执行的是 B"。

> 验收判据（比任何 checklist 都好用）：让一个没参与过这个系统的人，**一小时内**答出"上周三 tenant A 那个批量删数据是谁批的、当时的参数是什么、能不能 revert"。

## 6. 执行引擎的模块与边界

### 6.1 分层

```text
控制面  │ 租户 · 鉴权 · 配额/预算 · 配置与发布 · 凭证托管 · 审计导出
────────┼──────────────────────────────────────────────────────────────
执行面  │ 调度器 · 状态机 · agent runtime · 模型网关 · 工具网关
        │ 检索服务 · 护栏(guardrail) · checkpoint · 事件总线
────────┼──────────────────────────────────────────────────────────────
存储面  │ 事件日志 · 状态快照 · 对象存储(artifact) · 向量库 · 审计库
────────┼──────────────────────────────────────────────────────────────
观测面  │ trace · 指标 · 回放 · 评测集/门禁 · 灰度与回滚
```

### 6.2 边界规则

| 组件         | 唯一职责                                                           | 不允许做的事                                                                 |
| :----------- | :----------------------------------------------------------------- | :--------------------------------------------------------------------------- |
| **模型网关** | 通往模型 provider 的唯一出口：路由、重试、计费、缓存               | 被业务代码绕过直连 SDK（否则计量与限流全部失效）                             |
| **工具网关** | 通往外部世界的唯一副作用出口：鉴权、参数校验、风险分级、幂等、审计 | 让工具自己决定"要不要申请审批"                                               |
| **状态机**   | 进度的唯一真相来源（`fsm_state` / `next_actions`）                 | 其他组件私自改"我到哪一步了"                                                 |
| **调度器**   | 优先级、公平、租约、扩缩容                                         | 承载任何业务语义                                                             |
| **检索服务** | 无状态召回                                                         | 被当作"上下文管理器"塞进主循环（检索时机属于主循环，见 [RAG](../rag.md) §8） |
| **护栏**     | 在网关里 enforce 策略                                              | 靠 prompt 说服模型（见 [提示工程](../prompt_engineering.md) §8）             |

三条跨组件的约定，比任何架构图都重要：

- **所有副作用幂等**：工具网关强制要 `idempotency_key`，"幂等三件套"见 [状态管理与 Checkpoint](state.md) §4。
- **所有调用有身份**：`tenant_id` + `run_id` + `agent_id` 进 trace 与日志，缺一不可。
- **所有配置版本化**：模型、prompt、工具 schema、harness 配置（见 [版本化与灰度](rollout.md)）。

### 6.3 "从零设计一个执行引擎"的答题骨架

按顺序想，前四步决定架构，后三步决定能不能运营：

1. **先定边界**：哪些是"决策"（模型），哪些是"执行"（工具网关），哪些是"记账"（状态机 + 事件日志）
2. **先定状态**：什么进共享 state、什么只进消息流（外部材料永不进 state）
3. **先定幂等**：副作用清单 + 每个副作用的 key 生成规则
4. **先定租户维度**：即使只有单租户，也把字段和切分点留出来
5. 再补调度：优先级、租约、公平、dead letter
6. 再补护栏：预算树、循环检测、HITL、熔断
7. 最后补观测与灰度：trace → dataset → 门禁 → canary

> 反序是常见失败：先画一堆模块框，最后发现"预算归谁记、副作用谁保证幂等"两个问题没有答案——这两个问题不定，中间所有模块都要改。

## 7. 常见反模式

- **租户 ID 只活在请求头**：异步任务、回调、定时任务里丢掉，跨租户泄漏从这三处开始。
- **用 prompt 做配额与权限**："你最多花 10 块"写在系统提示里——模型不执行策略，网关执行。
- **扁平预算**：§4.2 的 10 倍超支，通常第一次跑并行 fan-out 就会遇到。
- **共享 service account**：审计日志全部记成"平台自己"，等于没有审计。
- **审计写业务库**：出事时业务库在回滚，审计记录跟着一起没了。
- **一个 agent 服务所有租户的所有场景**：应该用 per-request 动态构造（factory），见 [多 Agent 编排](../multi_agent.md) §6.2——但动态构造要注入一致的 trace 与租户元数据，否则可观测性倒退。
- **多租户压测只测单租户**：配额和隔离的 bug 只在"两个租户同时打满"时出现。

## 8. 上线前自检

- [ ] 任意一条 trace / 事件 / 计费记录能独立说出所属租户
- [ ] 缓存 key、向量 collection、临时目录、队列 topic 都带租户维度
- [ ] 成本按租户 / run / agent 三维可归因；有预算树，且 reserve 失败会 fail-closed
- [ ] 超限动作是可解释的业务事件（带剩余额度、重置时间）
- [ ] 审计只追加、可校验（hash chain 或 WORM）、与业务库分离
- [ ] 高危工具走工具网关，强制 `idempotency_key` 与风险分级
- [ ] 租户级压测跑过（两租户同时打满），隔离与配额都成立
- [ ] 配置（模型 / prompt / 工具 schema / harness）全部版本化，可回滚
