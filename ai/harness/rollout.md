# 版本化与灰度 (Rollout & Canary)

> 服务升级的死法通常是 5xx；agent 升级的死法是**静默的行为漂移**——接口没变、没有报错、成功率从 78% 掉到 71%，而且只掉在长尾 case 上。本篇讲怎么让这种漂移在发布前可见、发布中可控、出事后可回滚。

## TL;DR

- Agent 的"版本"不是一个镜像标签，而是**四类对象的组合**：模型、prompt（含工具描述）、工具 schema、harness 配置。任何一类变了，行为都可能变。
- 升级前必须先做**行为 diff**：拿历史 trace 回放新版本，比"工具序列 / 步数 / token / 终态"，产出一份差异 case 清单，而不是一个平均分。
- 三段式放量不可跳：**影子（只观察不写）→ canary（按租户放量）→ 全量**。跳段省下的一天，会在事故复盘时变成一周。
- 灰度判据以**早信号**为主（工具序列、步数、token 斜率、拦截率）。完成率是最后才动的指标，等它掉就已经是事故。
- 回滚单位是 **manifest**（四类对象一起），不是单个模型；"换了模型但留着新 prompt"这种半回滚比不回滚更难查。

## 1. 为什么 agent 升级比服务升级难

- **契约保护不了行为**：传统服务只要接口不变，行为基本不变；agent 在系统提示里加一句"回答尽量简洁"，工具调用序列就变了。
- **失败是静默的**：没有 5xx、没有异常堆栈。表现是"用户开始追问""人工接管率上升""某类任务开始绕路"。
- **变量同时变**：模型、prompt、工具 schema、上下文压缩策略、检索索引，任何两个同时改，出问题就归因不了。
- **重放不等于复现**：`temperature=0` 也不是确定性执行（浮点累加、推理引擎版本、batch 组成都会影响），想"重跑一遍看看"是不可靠的（见 [状态管理与 Checkpoint](state.md) §5）。

> 所以 agent 的发布单位是**版本组合（manifest）**，不是容器镜像。发布、评测、审计、回滚全都以 manifest 为准。

## 2. 版本化：四类对象 + 一份 manifest

| 对象             | 存在哪                              | 变了会怎样                                 | 怎么锁                                        |
| :--------------- | :---------------------------------- | :----------------------------------------- | :-------------------------------------------- |
| **模型**         | provider + model id + 具体版本      | 推理风格、工具选择倾向、拒答边界全变       | 不用 `latest` / `-preview` 别名；锁具体版本号 |
| **prompt**       | 模板文件 / DB 配置                  | 措辞、顺序、few-shot 都会改变行为          | 存模板 **hash**，与评测集一起版本化           |
| **工具 schema**  | JSON Schema + description           | **描述文本改了也算变更**：模型靠描述选工具 | schema 版本号 + 描述 diff 进 review           |
| **harness 配置** | stop rule、预算、压缩策略、重试策略 | 步数上限、降级路径、成本上限全变           | 配置即代码，不允许"线上手改"                  |

再加一类容易被忘的：**检索索引**。embedding 模型一换就必须重建整个索引，否则是静默错误（见 [RAG / 知识检索](../rag.md) §10）。

### 2.1 manifest

每个 run 落一份，进 trace、进审计、进评测集的每一行：

```json
{
  "run_id": "run_9f3",
  "versions": {
    "model": "anthropic/claude-sonnet-5-5@2026-09-01",
    "prompt_hash": "sha256:7c1e...",
    "tool_schema": "tools@v14",
    "harness": "harness@v22",
    "retrieval_index": "kb-prod@2026-10-20",
    "config": "canary-a"
  },
  "started_at": "2026-10-27T09:12:03Z"
}
```

> 验收判据：能不能回答"上周那个 badcase 跑的是哪套版本组合"？答不出来，就没法回放、没法归因、没法证明"是这次升级导致的"。

## 3. 发布前的两道门

### 3.1 离线门禁

固定评测集跑新 manifest，与 `last_known_good` 比——指标分层用**目的轴**（能力 / 对齐 / 回归 / 红队），别只看一个总分（定义见 [评测](../evals.md)）。

门禁要拦的是"不能发"，不是"不好看"：核心集掉点、对抗集出现新的注入成功、权限用例越权，任何一条命中就阻断。

### 3.2 行为 diff（比分数更有信息量）

拿线上 trace 抽样回放新版本，逐字段比：

| 比什么               | 为什么         | 典型异常                                 |
| :------------------- | :------------- | :--------------------------------------- |
| 终态（outcome）      | 任务是否还完成 | 成功率掉 2% 以上                         |
| 工具调用序列         | 过程是否等价   | 原来 3 步现在 7 步、开始绕开某个工具     |
| 步数 / turn 数       | 效率           | 平均值 +40%（成本跟着涨）                |
| token 斜率           | 上下文膨胀     | 每轮 token 递增，说明压缩失效            |
| 安全拦截 / HITL 触发 | 行为边界       | 拦截率突然下降（模型开始试图做危险操作） |

**输出是一份 case 清单，不是一个平均数。** 平均分会同时掩盖两件事：成功率没掉但成本翻倍，以及"某类任务彻底坏掉但占比只有 2%"——而后者正是长尾用户最先撞上的。

> 行为 diff 的前提是 trace 能转成 dataset（`(input, expected_trajectory, expected_outcome)`），接口见 [可观测性](observability.md) §5。
>
> **它也是跨团队分歧的降级工具**：算法、后端、产品对"这个改动该不该发"争执不下时，**别投票、别开会——一起看同一条 trace 回放**。回放把"我觉得"变成"你看这一步"，把政治问题降级成事实问题。这是我在跨团队推进里唯一稳定有效的招。

## 4. 三段式放量

| 阶段               | 流量                     | 有副作用吗                 | 看什么                                     | 进入下一阶段的条件               |
| :----------------- | :----------------------- | :------------------------- | :----------------------------------------- | :------------------------------- |
| **影子（shadow）** | 镜像真实请求，结果丢弃   | **否**——只读凭证 / dry-run | 它"想做什么"：工具选择、危险动作倾向、成本 | 无新增高危意图、成本在预算内     |
| **canary**         | 1–5%，按 **租户** 分桶   | 只放开低危工具             | 早信号 + 抽检 + 人工接管率                 | 早信号无显著差异，抽检无新类失败 |
| **全量**           | 分批（10% → 50% → 100%） | 全部                       | 全量指标 + 客诉                            | 全量指标回到基线                 |

三个落地细节，漏了就会踩：

- **影子是双份成本**。目标流量 × 新版本 token，预算树里要单独预留（见 [Agent 平台化](platform.md) §4）。
- **canary 按租户分桶，不按请求分桶**。同一租户一半请求走新版本，用户体验不一致，而且长时 session 会跨版本串状态。
- **长时 running session 会跨版本存活**。灰度切的是"新开的 run"，正在跑的 30 分钟任务还在旧版本上——回滚时这批 session 是灰区，要么等它跑完，要么强制 checkpoint + 重启。

## 5. 灰度期看什么：早信号 vs 晚信号

| 信号                     | 出现在   | 灵敏度 | 用途                                       |
| :----------------------- | :------- | :----- | :----------------------------------------- |
| 工具调用序列分布         | 分钟级   | 最高   | 第一道警报，几乎不滞后                     |
| 步数 / turn 数           | 分钟级   | 高     | 发现"绕路"和"原地打转"                     |
| token 斜率               | 分钟级   | 高     | 上下文压缩失效的先行指标                   |
| 安全拦截率 / HITL 触发率 | 分钟级   | 高     | 行为边界漂移（上升=变激进，下降=护栏失效） |
| 延迟 P95                 | 十分钟级 | 中     | 换模型/加检索的直接后果                    |
| 完成率 / 接管率          | 小时到天 | 低     | 最有说服力，但最晚到                       |

> **判据设计要点**：用早信号做**自动回滚**的触发器，用完成率做**事后归因**的证据。反过来（等完成率掉了才回滚）等于让用户先踩一遍坑。

## 6. 回滚

### 6.1 回滚单位

回滚 **manifest**，四类对象一起回到上一个 `last_known_good`。所以 manifest 必须有 history 与显式的 good 标记。

### 6.2 自动回滚阈值（示例，按业务校准）

- 完成率相比对照下降 > 3%
- 平均步数上升 > 30%
- 单 run 成本上升 > 40%
- 安全拦截率上升 > 2×（或下降到接近 0——同样危险）
- 延迟 P95 上升 > 50%

任一条命中即回滚，先把血流止住，再分析。**不要设计"满足三条才回滚"**——那只是把决策拖到事故之后。

### 6.3 三个容易翻车的点

- **状态 schema 兼容性**：新版本把 state / 事件写成了新格式，回滚后旧版本读不懂 → 状态要么带 schema 版本号并双向兼容，要么回滚前先跑迁移的逆操作。
- **半回滚**：只回模型、留着新 prompt，或只回 prompt、留着新工具 schema。行为是"两个版本的混合"，比任一单版本都难解释。**要么整组回，要么不回。**
- **已发生的副作用回不来**：发出去的邮件、合并的 PR、扣掉的钱只能**补偿**（`git revert`、反向操作、退款），不能"回滚"。所以高危工具在 canary 阶段也不该放开（见 [沙箱与权限执行](sandbox.md) §4）。

### 6.4 provider 侧静默升级

模型 id 不变、背后的权重变了——这是最隐蔽的一种"我们没发布但行为变了"。对策是**定期行为指纹**：每天/每周用一组固定的金标 case 跑当前生产 manifest，与历史 baseline 比早信号。漂移超阈值就当"被动升级事故"处理，走同一套回滚/换版本的流程。

## 7. 常见反模式

- **用 `latest` 别名**：等于把版本控制交给 provider。
- **prompt 改了不进版本控制**：运营在后台改一句话，评测集与 trace 全都对不上。
- **一次改两个变量**（换模型 + 改 prompt）：任何结果都无法归因，只能全量回滚。
- **影子阶段就放开写权限**：影子必须是"只读 + dry-run"，否则它就是一次没有 canary 保护的全量发布。
- **只灰度新请求，不管长时 session**：一半流量在新版本、一半在旧版本，指标全是混合值。
- **拿平均分验收**：见 §3.2，平均值会同时掩盖成本翻倍和长尾崩塌。
- **回滚靠人肉**：发现要 20 分钟、决策要 30 分钟、操作要 10 分钟——小时级恢复对 agent 系统太慢。

## 8. 上线前自检

- [ ] 四类对象 + 检索索引都有版本号，`latest` 全部消除
- [ ] 每个 run 落 manifest，能回答"这个 badcase 跑的是哪套版本"
- [ ] 有 `last_known_good` 标记，回滚是一条命令/一个开关
- [ ] 行为 diff 跑得起来（trace → dataset → 回放 → 差异清单）
- [ ] 影子模式可用（只读凭证 / dry-run 工具），且预算里留了双份成本
- [ ] canary 按租户分桶；长时 session 的跨版本策略已明确
- [ ] 自动回滚阈值写死在配置里，不是写在文档里
- [ ] 状态 / 事件 schema 变更经过回滚兼容性 review
- [ ] provider 侧静默升级有行为指纹在跑
