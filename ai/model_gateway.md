# 模型网关 (Model Gateway)

> 上一篇 [自建推理服务](inference_serving.md) 讲的是"自己托管模型"；本篇讲它的对偶：**同时对接多家模型 API 时，那一层薄但不薄不可的适配层**。
>
> 在 [Agent 平台化](harness/platform.md) §6.2 的边界表里，模型网关只占一行（"通往模型 provider 的唯一出口"）。这一行底下藏着 wire family、能力声明、错误归一、流式累计、计量口径五件麻烦事。

## TL;DR

- **按 "wire family" 建模，不要按 "厂商" 建模**。同一个厂商可能有多个 wire 面（OpenAI 的 `responses` 与 `chat`），不同厂商可能骑同一个 family（DeepSeek / GLM 走 OpenAI wire）。**配置里的 id 命名的是"部署"，不是"模块"**。
- **方言（dialect）不是配置，是推导结果**：deployment 写 spec，driver 从 spec 得出"这个实例该用哪个 wire 面、reasoning 怎么往返、溢出怎么截断"。把这些散在 if-else 里，第一次加厂商就会失控。
- **能力用"声明 + 校验"而不是"探测为主"**：声明可预测、启动即失败；探测自适应但慢且不确定。最佳组合是**声明为主 + 首调校验 + 明确降级**。
- **错误码必须归一到三类才能重试**：`rate_limit` / `timeout` / `unavailable`。各家的 429/529/1002/422 语义不同，直接按状态码重试必然出错。
- **流式路径的 usage 常常最后一帧才到**，中断就拿不到——所以流式必须有 accumulator，且计费要能"按估算 + 标记待校准"。

## 1. 这一层到底在做什么

五个职责，少一个就会把复杂度泄到业务代码里：

| 职责         | 具体内容                                                      | 失败时的表现                       |
| :----------- | :------------------------------------------------------------ | :--------------------------------- |
| **路由**     | 把"某个模型 id"解析成"某个 driver + 某个 endpoint + 某个方言" | 加一家厂商要改 N 处业务代码        |
| **形态转换** | 内部 message/tool/stream 模型 ↔ 各家 wire 格式                | 每家一个 if-else 分支，越加越乱    |
| **错误归一** | 各家错误码 → 统一错误分类 → 重试/降级决策                     | 到处 `if status == 429`            |
| **计量**     | token / 缓存 / 思维链的字段口径                               | 账单和自建统计对不上               |
| **流式**     | delta 事件累积、结束判定、用量补全                            | 中断的请求没有 usage，成本算不出来 |

## 2. wire family，而不是"支持 N 家"

最容易走错的一步是把"厂商"当建模单位。真实结构是：

```text
family: openai-wire      family: messages-wire      family: vendor-native
├── openai               ├── anthropic              ├── bytedance
├── azure (routing)      └── (其它兼容者)           ├── minimax
├── deepseek                                        └── dashscope
└── glm
```

三条推论：

- **一个 family 一套转换代码**，新增一家兼容厂商 = 加一个 declaration，不是加一份 driver。
- **同一厂商可能有多个 wire 面**：OpenAI 的 `responses` 与 `chat` 是两套事件模型；Anthropic 的 Messages 是另一套。**这是"方言"的第一维**。
- **id 命名部署，不命名模块**：文档里写 `provider: deepseek` 指的是"这个部署连的是 DeepSeek 的端点"，实现上它跑在 OpenAI driver 上。把这两件事混起来，代码里就会出现 `if provider == "deepseek"` 这种永久性技术债。

## 3. dialect：spec 写什么，driver 推导什么

> spec 是部署方写的（端点、模型名、参数）；dialect 是 driver 从 spec **推导**出来的（该走哪个 wire 面、reasoning 怎么往返、溢出怎么处理）。

真实存在的 dialect 维度（以 OpenAI family 为例，其它 family 各有自己的）：

| 维度                   | 取值                                                                  | 为什么必须显式建模                                     |
| :--------------------- | :-------------------------------------------------------------------- | :----------------------------------------------------- |
| **wire 面**            | `responses` / `chat`                                                  | 事件模型、工具调用回填格式、usage 字段全不同           |
| **reasoning 通道**     | `summary`（摘要 + 不透明加密块）/ `text`（纯文本并进 assistant 消息） | 前者**回传时原样带回加密块**，后者不能伪造；混用会 400 |
| **reasoning 摘要策略** | `auto` / `concise` / `detailed`                                       | 影响可读性与 token；空值 = 不要摘要（≠ auto）          |
| **截断策略**           | provider 侧 overflow 行为                                             | "超长报错"和"悄悄截断"是两种语义，后者会静默丢上下文   |
| **缓存控制**           | 显式 breakpoint / 自动前缀                                            | 决定 token 计费口径（cache_read 与 input 不是一个价）  |

> **反直觉**：reasoning 的往返不是"把思维链存下来再发回去"。带加密块的实现里，你**存的是不透明 payload**——不能解析、不能编辑、不能跨模型复用。想"用 A 模型的思考喂 B 模型"，在这个形状下根本做不到，别设计依赖它的功能。

## 4. 能力：声明 vs 探测

| 方式                                                    | 优点                             | 缺点                                     | 适用                 |
| :------------------------------------------------------ | :------------------------------- | :--------------------------------------- | :------------------- |
| **声明**（spec 里写 capabilities，启动时 `Validate()`） | 可预测、启动即失败、可做静态检查 | spec 会过时；厂商悄悄加/减能力时你不知道 | 生产默认             |
| **探测**（启动或首调时试一发）                          | 自适应、能发现真实上限           | 慢、要额外配额、探测本身可能被限流或计费 | 灰度、多租户自助接入 |
| **混合**（声明为主 + 首调校验 + 明确降级）              | 两者兼顾                         | 代码量翻倍                               | 我推荐的形态         |

声明式要落成**可校验的枚举**（输入模态、输出模态、工具调用、并行工具、结构化输出、自定义 embedding 维度……），而不是一堆 bool 散在结构体里——否则"这个模型支不支持并行工具调用"永远没人说得准。

> 关键判据：**能力不对时是"启动失败"还是"运行到一半 400"**。前者是工程，后者是事故。所以声明式校验必须在启动/装配期跑完。

## 5. 错误归一：先分类，再重试

各家错误码语义差别很大，真实例子：

- 同一件事在不同家的编号不同（某家限流是 `429`，另一家是业务码 `1002`，还有一家把"过载"叫 `529`）。
- **同一个状态码在不同家语义不同**：`403` 可能是"key 缺失"（该报配置错误、不该重试），`401` 可能是"key 错"（同样不该重试），而 `429` 才有可能是"等一下就好"。

归一的落点是**重试分类**，不是"复制原始错误"：

```text
rate_limit    → 可重试（带 Retry-After，退避）
timeout       → 可重试（但要看总预算）
unavailable   → 可重试（对方过载，退避更激进）
其它 4xx      → fail-fast，重试只会浪费预算
```

工程上要额外的三件事：

- **策略按操作类型分开**：generate / embed / transcribe 的失败模式与代价不同，一套重试参数管不了。
- **`fallback_on_retry_exhausted`**：重试耗尽后是"换目标"还是"报错"，必须是显式配置项——默认行为不该是静默换模型（你会悄悄换了质量）。
- **退避要有上限与抖动**：见 [韧性](harness/resilience.md) §2；这里只强调"重试预算"要跟着预算树走（见 [Agent 平台化](harness/platform.md) §4）。

## 6. 流式：三个必踩的坑

1. **usage 常常最后一帧才到**。用户在第一个字出现时就可能中断，此时你**没有 token 数**。对策：流式必须挂 accumulator，结束时落"最终用量"；中断时落"估算用量 + `estimated: true`"，之后可校准。
2. **事件粒度不同**：有的 family 每个 token 一个事件，有的是"增量 + 完整快照"混合。accumulator 必须按 family 实现，不能在网关层做一个"通用拼接"——那是所有流式 bug 的源头。
3. **结束判定不能只看 EOF**：正常结束、内容过滤截断、达到 max_tokens、工具调用等待，这四种的结束帧不一样，而**它们的处置完全不同**（前者成功，后两者可能是失败或需要继续）。

> 一句话：**流式不是"把 SSE 转成 channel"，是把"这次调用到底发生了什么"完整重建出来**。重建不了，观测和计费都是错的。

## 7. 计量：字段表要能被词汇表钉住

token 计量的难点不是"记一个数"，是**口径**：

- 一次请求的 token 不是一个数，而是**按内容分段**的（文本 / 图片 / 音频 / 视频 / 文件 / 数据 / 工具调用 / 工具结果 / reasoning）。
- 同一批内容在"上下文"和"本次输入"两个位置可能都算钱，也可能只算一次——**取决于 family**。
- 缓存要分 `cache_write` / `cache_read`，单价差一个数量级（见 [可观测性](harness/observability.md) §3.1）。

可维护的做法是**把"内容种类 × 位置"建成立字段表**，并写一个测试把表钉在词汇表上——这样"新增一种内容类型忘了计费"会在 CI 里挂掉，而不是在月底账单里暴露。

## 8. 配置边界要严格解码

网关的配置是最容易被手写错的东西。两条硬规则：

- **`DisallowUnknownFields`**：拼错的字段必须报错，不能静默变成零值。`max_tokens` 写成 `max_token` 而"恰好能跑"，是最贵的一类 bug（你会以为改的是 A，实际什么都没改）。
- **未知枚举立即失败**：`truncation: "truncat"` 不能 fallback 到默认值。

## 9. 常见反模式

- **按厂商写分支**：`if provider == "deepseek"` 一旦出现，后面每家都要加一次。
- **把 dialect 写进配置**：让用户手填"该用 responses 还是 chat"，等于把内部推理结果外泄成配置项，用户填错你还要兼容。
- **用状态码做重试判断**：`5xx` 里既有可重试的过载，也有不可重试的实现 bug。
- **流式路径不做 accumulator**：结果是"非流式有精确用量、流式只有估算"，报表永远对不上。
- **重试耗尽后静默换模型**：质量变了没人知道，查一周。
- **网关透传原始 error**：上层要认识五家的错误格式，等于没有网关。

## 10. 上线前自检

- [ ] 一家厂商 = 一个 declaration（不是一份转换代码），新增兼容厂商不改核心
- [ ] dialect 由 driver 推导，不出现在用户配置里
- [ ] 能力声明有 `Validate()` 且跑在装配期；不支持的能力是"启动失败"
- [ ] 错误归一到 `rate_limit` / `timeout` / `unavailable` + fail-fast 四类
- [ ] 重试策略按操作类型分开；`fallback_on_retry_exhausted` 是显式配置
- [ ] 流式有按 family 实现的 accumulator；中断能落估算用量并标记
- [ ] 计量字段表按"内容种类 × 位置"建表，并有测试钉住词汇表
- [ ] 配置解码 `DisallowUnknownFields`，未知枚举立即失败
- [ ] 网关是唯一出口：业务代码不直连 provider SDK（否则路由/计量/限流全失效）
